The shipped scene is deliberately almost empty. It holds one GameLifetimeScope, five UI and camera objects, a finish trigger and an empty TrackRoot. The track, the racers, the mud, the boost pads, the gusts, the gates and the crowd are all generated at runtime by Systems_TrackBuilder and Systems_Spawn. That is why the scene file is 32 KB while a training scene is 159 KB.

The shipped scene list is explicit, and for a reason. Editor_BuildAndroidAAB.SHIP_SCENES hardcodes Assets/Scenes/SCN_RACE_FLAT.unity as scene 0 — it does not read Unity's Build Settings, because Build Settings also carries the three training scenes. Depending on their order those would bloat the bundle and, worse, could boot a tester straight into a training rig. A scene named in SHIP_SCENES that is missing on disk aborts the build.

Three UIDocuments, zero Canvases. The project is 100% C#-built UI Toolkit — no UGUI, no IMGUI, no .uxml or .uss assets anywhere. com.unity.ugui and TextMeshPro were removed from the manifest on 2026-08-29 after being confirmed unreferenced. All three documents share RaceHudPanelSettings, which scales on width against a 420 dp reference so one UI unit is roughly one dp on a real handset.
Screen furniture is fixed at five anchors, identical on every screen: game name upper-left, FPS top-centre, MENU upper-right, Application.version lower-right, DBG lower-left. All on the inset safe layer, non-pickable where they are not controls, and outside any ScrollView. DebugOverlayView owns the FPS readout — do not add a second one to RaceHudView; they share an anchor and draw over each other.

What gets built at runtime

Systems_TrackBuilder → under TrackRoot

  • Ground slab, sized to the chosen map's length and a fixed 24 m width
  • Terrain displacement for Lumpy and Swamp
  • Obstacle boxes, gate walls, mud volumes, boost pads, gust volumes
  • Crowd stands along the lane edges

Eight TrackKind values exist (Flat, Hills, Bumps, Walls, Rough, RoughBlocked, Lumpy, Swamp) but only four are reachable from the menu; Rough and RoughBlocked are training-only until brains are retrained on them.

Systems_Spawn → the grid

  • Instantiates from CreatureCatalog per RaceConfigModel counts
  • 10 columns, 2 m apart, rows 1.6 m back — a marathon start
  • Past 30 racers it stacks in layers 1.5 m apart with 0.35 m jitter, three rows deep per layer
  • Staggers DecisionStep by gridIndex % 5 so decisions spread across frames
  • Applies visible quirks — power, mass and friction spread — with a HUD badge and a name prefix
  • Sets MaxStep = 0: a racer is never episode-capped, only despawned
  • A racer whose .onnx is missing is skipped with a warning. The race never crashes

Race scene geometry — Flat map

To scale on the long axis. Lane width is fixed at 24 m so the 10-wide grid fills the frame visually, whatever the race length.

Three of those brokers were dead until recently. RacerWipeoutMessage, RacerOvertakeMessage and PhotoFinishMessage were declared and published but never registered in the LifetimeScope — so VContainer handed every publisher and subscriber the null default their optional constructor parameter allowed. Wipeout audio, the wipeout camera shake, the photo-finish sting and its commentary line were all silently doing nothing. The lesson: an optional IPublisher<T> parameter turns a missing registration from a startup exception into a feature that quietly never fires.
Two objects need forced construction or ordering. Systems_Elo has no tick or start interface, so RegisterBuildCallback resolves it eagerly — otherwise its RaceFinishedMessage subscription would not exist when the first race ended. And Agent_IsaacBox carries [DefaultExecutionOrder(100)] so it runs after IsaacBoxAgent.Start has built the inference worker, before parking it.

How an area reads the curriculum

On every reset, guarded by Academy.IsInitialized so it is a no-op in a race, the area pulls all eight environment parameters and clamps each one. The clamps are the real ceilings — a config asking for more than these gets silently trimmed.

ParameterDefault when absentRuntime clamp
goal_distance_max20 mfloored at MIN_GOAL_DISTANCE 3 m
goal_angle_span0°0 … 45°
rough_amplitude1.00 … 1
track_kindthe area's authored _trackKindrounded to a TrackKind value
hazard_level00 … 2 (integer)
quirk_power_span00 … 0.5
quirk_mass_span00 … 0.3
quirk_friction_span00 … 0.5

Note the headroom: the race-day curriculum tops out at quirk_power_span 0.08 against a clamp of 0.5, and quirk_mass_span 0.12 against 0.3. The clamps are safety rails, not the schedule. rough_amplitude is the exception — it writes a static Systems_TrackBuilder.RoughAmplitudeScale, so every area in the scene shares one value, which is fine only because all areas advance on the same progress clock.

The TRAINING_MAX_STEP comment is stale, and the number it describes has quadrupled. Source says // 60 s at 0.02 s per step, which was true when one agent step was one 0.02 s physics tick. Today MaxStep counts decisions, and a decision is DecisionPeriod 20 × Δt 0.005 s = 0.1 s — so 3,000 steps is 300 s of simulated time, not 60. Combined with the configs' time_horizon: 1000, GAE truncates three times inside a single full-length episode. The cap itself is harmless (the stall timer fires long before it), but the comment will mislead the next person to tune it.

Why SCN_TRAIN_ALL holds creatures that no longer race. Builds/AllEnv is built from this scene, so it contains all thirteen behaviours — and mlagents aborts at startup on any behaviour present in the env but absent from the config. That is exactly what killed run all8h_20260826_2233. It is also why BrokenLoco01.yaml lists Quad, Hexapod, Kangaroo and Blob even though it only cares about Worm, Spider, Centipede and Crab.
Training scenes have no LifetimeScope, on purpose. ML-Agents Agent subclasses have an explicit carve-out from the MVS pattern: they own their observation, action and reward logic, take no VContainer dependencies, and the reward maths lives in a plain-C# Reward_* class so it stays unit-testable. A training scene therefore needs no DI container at all — which is also why a training scene accidentally shipped in a build would boot into nothing recognisable.

SCN_TEST_ISAACBOX — three objects

SCN_TEST_ISAACBOX ├─ IsaacBox_Camera Camera — no CinemachineBrain, no AudioListener ├─ IsaacBox_Ground MeshRenderer ×2 · MeshCollider — a plain plane; no TrackBuilder involvement └─ IsaacBox_Light Light · UniversalAdditionalLightData

The IsaacBox prefab is not in this scene — it is dropped in by hand, or added by PoRacer ▸ Creatures ▸ Register IsaacBox Racer. The scene exists so the rig can be watched walking without a race, a menu, a HUD or a LifetimeScope in the way. It is currently modified in the working tree and is not in SHIP_SCENES.

The IsaacBox prefab holds no ArticulationBody at all. IsaacBoxAgent builds the 22-link, 21-joint articulation at runtime from isaacbox_rig.json, reading per-joint stiffness, damping and effort limit out of the same file the Isaac Lab side reads. That is what keeps the Unity rig and the trained rig from drifting apart — but it also means the hierarchy you see in the Editor is not the hierarchy that races.
Fido needs one scene-order rule. Systems_MujocoWorld must build its MjScene, ground plane and solver options before the first Fido is instantiated. Every MjComponent.OnEnable reads MjScene.Instance, and that getter creates an MjScene if none exists — so building second throws "singleton, yet multiple instances found". Related: mujoco.dll is a native plug-in that loads at Editor startup only, so moving it requires an Editor restart before anything MuJoCo works.
