(`armatureMode = FoldIntoInertia`) precisely to recover that conditioning.

## C. Explicit-PD stability bound  `kd * dt / I_joint`

Applies to the **diagnostic** `ActuatorMode.ExplicitTorquePD` path only
(`tau = clip(kp*(q* - q) - kd*qd, +/-effort)` applied with `ArticulationBody.AddTorque`).
The shipped default is `ArticulationDrive`, an implicit spring-damper, which is
unconditionally stable and does not obey this bound.

`I_joint` is the whole distal subtree's inertia about the joint axis at the default
pose (parallel-axis, every body). Explicit damping goes unstable as `kd*dt/I -> 2`.

### Parent-recoil caveat

`kd*dt/I < 2` is a single-joint bound. It treats the parent as infinitely massive, so
it is optimistic for a serial chain: a joint whose parent is comparable in inertia
recoils, and the effective ratio is worse than the table says. A joint sitting at
ratio ~1.5 at 1/240 can still diverge in practice. Treat the coarsest passing step as
an upper bound to be confirmed empirically, not as a licence - which is exactly what
rung 3 (zero-g square wave) measures, and why `ExplicitTorquePD` ships as a
diagnostic switch behind `ArticulationDrive` rather than as the default.

### What was actually measured in Unity

The table above is a bound, not a result. In the engine, with `armatureMode = None`
(the shipped default, see section A), `ExplicitTorquePD`:

| step | outcome |
|---|---|
| 1/500 s | **diverges** - zero-g bang-bang max abs vCoM 34.2 m/s, 58.7 m of drift in 3 s; falls immediately under gravity |
| 1/1000 s | **walks** - 0.956 m/s, upright 0.991, height 0.914 m |

So the usable figure is **1/1000 s**, consistent with the no-armature column above
(1/960 -> 0.82) and NOT with the with-armature column. The with-armature column is
informational only: folding the armature into link inertia is what the shipped
configuration deliberately does not do.

Concretely: the worst joint at this project's step is **`left_shoulder_yaw` at 1.70**, and its
parent-side subtree is only 2.66x its own inertia, so the
single-joint number is meaningfully optimistic for exactly the joint that is closest to
the limit. **`ExplicitTorquePD` therefore ships with a recommended substep of 0.004167 s** (worst ratio 0.35), a 4x margin rather
than the 1.2x the raw bound would allow. `IsaacH1Agent` logs that substep when the mode
is selected; it does **not** change `Time.fixedDeltaTime` to reach it.

| as `wxyz` | 1.922e+00 | 1.729e+00 | mismatch |
| as `xyzw` | 8.312e-03 | 3.344e-05 | **MATCH** |

**The field is `xyzw`, despite being named `..._wxyz`.** Reading it as `wxyz` gives a 1.73 mean error - the robot would be
interpreted as upside down. `isaac_reference.json` in this folder is a copy with the
field renamed `root_quat_w_xyzw` so the name states the real order.

The corresponding Unity conversion is therefore
`new Quaternion(q.y, -q.z, -q.x, q.w)` reading `q` as **xyzw**, i.e. the Unity vector
part is `-M * (x,y,z)` and the scalar is `w`.

## Control rate

| quantity | value |
|---|---:|
| Isaac `policy_dt` | 0.02 s (50 Hz) |
| Isaac `physics_dt` | 0.005 s (200 Hz) |
| Isaac decimation | 4 |
| this project's `Time.fixedDeltaTime` | 0.02 s (50 Hz) |
| **policy_dt / fixedDeltaTime** | **1.000000** |
| integer? | **yes** |
| shipped decimation | 1 |

The ratio is an exact integer (1), so the agent runs at the project step
with no rounding and logs **no** `LogError`. It does log one `LogWarning`, because
decimation 1 is not Isaac's 4: the PD drive
gets 1 tick(s) per policy step where Isaac gave it 4.
